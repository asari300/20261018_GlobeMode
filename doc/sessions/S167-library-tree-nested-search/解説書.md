## 1. 目的

[S164 の点検](../../research/app-flow-2026-11-05.md)の穴 1（N1）。ライブラリの木は 1 ファイル 1 項目で、ファイルの中で定義された入れ子のクラスに行けなかった（`Modelica.Blocks.Examples` の 32 本、`Modelica.Blocks.Sources.Sine` など）。MSL の例題 553 本（partial を除く）のうち 123 本が木から選べず、検索欄も無かった。木に入れ子のクラスを出し、木の上に検索欄を置いて、キーボードだけで目的のクラスを開けるようにする。[S127](../S127-ui-library-tree/解説書.md) の「次回」の 2 項目（検索、1 ファイルのパッケージの中の入れ子）にあたる。

## 2. 決定と理由

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 入れ子の出し方 | `LibraryTree::new` が、各ファイルを字句解析（`lex`）して文を切り出し（`structure::split`）、`class_defs` でファイルの中のクラス定義を全部取り、同じ索引に入れる。短いクラス（`type X = Real;`、`connector RealInput = input Real;`）も葉として入れる | 整形器が使う道で、依存が増えず wasm でも動く。`globe-mode-fmt` は依存 0 のまま。展開は今までどおり索引の直下の子を引くだけ（`children` は変えていない） |
| なぜ展開のときに解析しないか | しない。索引は読み込み時に 1 回作る | 検索が入れ子のクラスを含めて引くには全ファイルの分が要る。字句解析だけなので軽く（下の測定）、Rumoca の構文解析（MSL 全体で数秒〜）は使わない |
| 正しさ | MSL 4.1.0 の全 2,552 ファイルで、アウトライン（`globe outline --json`、Rumoca の構文解析）のクラスの一覧と比べ、入れ子を含む 6,487 件が過不足なく一致した | 字句だけの読みがずれていないことの確認。一致しない所があれば、その原因を直す（下の整形器の誤り） |
| 開くもの | 入れ子の項目の `file` は、それを定義するファイル。押すとそのファイルを開き、モデル名に完全修飾名（`Modelica.Blocks.Examples.PID_Controller`）を入れる | S127 と同じ動き（`librarySource` は変えていない）。ファイルの中の行へ飛ぶことはしていない |
| 子を持つモデル | 子を持つ package は展開だけ。package 以外で子を持つクラス（関数を持つ block など）は、展開の ▸ に加えて「開く」のボタンを出す | そうしないと、子を持つモデルが開けなくなる |
| 検索 | 名前の部分一致（ASCII の大文字小文字を区別しない）。検索語に `.` を含めると完全修飾名に当てる。並びは名前が完全一致、前方一致、部分一致の順、同じ中では浅い順（パスが短い順）、次に名前の順。最大 50 件 | 一致の計算は Rust（`LibraryTree::search`）。Svelte は結果を選ぶだけ |
| 口 | `Backend.librarySearch(query)`、wasm `library_search(query, limit)`、LSP `globe/librarySearch`。Desktop の Rust は rpc が method をそのまま通すので変えていない | 木の項目と同じ形を返す。`tree_entries_json` を LSP に 1 つ置き、wasm も使う（JSON の組み立ての重複を避ける） |
| キーボード | 検索欄は `role="combobox"`、結果は `listbox`。↓↑ で選び、Enter で開き、Esc で消す | 検索欄に打つ、Enter、で開くまでマウスが要らない |

### 整形器の誤りを 1 つ直した

アウトラインと突き合わせると、`Modelica.Media` の 1,071 クラスが木に出なかった。原因は `structure::split` の `model extends X(修飾)` の読みで、修飾の閉じ括弧を `scan_to` で探していたが、`scan_to` は括弧の深さが負になると断るので、`redeclare model extends BaseProperties(p(stateSelect = …), …)` のように括弧が入れ子の修飾では必ず「閉じ括弧が多い」になっていた（整形器でこの形のファイルを整形できなかった）。括弧の対を読み飛ばす `skip_group` に置き換えた。MSL の `Media` の数ファイルが整形器でも読めるようになる。


## 4. 再現手順

```bash
export CARGO_TARGET_DIR=…/.git-worktree/target-shared CARGO_BUILD_JOBS=2
cargo test -p globe-mode-fmt tree
cargo test -p globe-mode-lsp library_tree
cargo test -p globe-mode-wasm --test decay library_tree
mise run wasm:node          # smoke.mjs が MSL の木と検索（PID_Con）まで確かめる
cd src/Svelte && pnpm check && cd ../..
uv run python src/Svelte/tests/test_ui.py   # MSL.json があれば、検索 PID_Con と木の両方
```

測定の結果（数字）:

| 項目 | 値 |
| --- | --- |
| 対象 | MSL 4.1.0 の `.mo` 2,552 ファイル（14.7 MB）。索引は 6,487 件の入れ子のクラス（と最上位） |
| 索引を作る時間（ネイティブ、release） | 79〜94 ms（`lex` + `split` + `class_defs`、数回の幅） |
| 索引のメモリ（ネイティブ） | 最大 RSS 25 MB。本文 14.7 MB を含むので、索引と作業の分は約 10 MB |
| MSL を読む時間（wasm、Node、`new Workspace(json, "MSL")`） | 変更前 223〜312 ms、変更後 346〜391 ms（3 回ずつ、load average 6〜9 の中で。差は索引の分の 100〜150 ms） |
| wasm の線形メモリ | 変更前も後も 63 MiB（索引の分は MiB の単位に出ない） |
| 検索の応答（wasm、Node） | `PID_Con` 2〜8 ms、`s`（50 件に打ち切り）5〜6 ms。全 6,487 件を毎回走査して並べ替える。100 ms の目安に収まる |
| ブラウザ（test_ui.py） | 検索欄に打ってから候補が出るまで 0.03〜0.3 s（Worker の往復と描画を含む） |

どちらにしたか: 依頼の選択肢のうち「MSL を読むときに作る軽い索引（既存の字句解析で）」にした。ファイルの中のクラスを「開いたファイルの分だけ」にとどめる案は、検索に `Sources.Sine` のような部品が出ないので採らなかった。Rumoca の `Outline` を引く案は、全ファイルの解析が要るので採らなかった（アウトラインは正しさの突き合わせにだけ使った）。

例題が木に出る本数（`msl-funnel` と同じ規則で選んだ 566 本のうち partial を除く 553 本。`globe outline --json` の一覧から数え、木の索引では「祖先が全部、索引にある」ことを確かめた）:

| | 木に出る | 木に出ない |
| --- | --- | --- |
| 変更前（1 ファイル 1 項目） | 430 本 | **123 本** |
| 変更後 | 553 本 | **0 本** |

テスト: `cargo test -p globe-mode-fmt`（木の試験 4 本を含む 10 本）、`globe-mode-lsp` の `library_tree_and_source`、`globe-mode-wasm` の `library_tree_opens_a_model_file_as_the_document`、`mise run check`（659 本 ok）、`pnpm check`（0 errors / 0 warnings）、`test_ui.py`（ok、`GM-SMOKE` の `tree=ok` は項目を足さず変わらない）。
