## 1. 目的

3 回目のレビューが立てた GitHub issue のうち #112（SSP）・#110（MSL の分割配信）・#117（VS Code のパネル）を、本文と現在のコードで確かめて直す。issue は閉じない。SSP は読み取り側（`globe-mode-fmi/src/ssp.rs` の `Walk`）だけを変え、書き出し（`globe-mode-fmi-import`）は別の担当（S318）が触っているので変えない。

## 2. 決定と理由

| issue | 監査の結論 | 直したか | 理由 | 試験 | 原則 |
| --- | --- | --- | --- | --- | --- |
| #112 SSP の階層名の長さと要素数に上限が無い | 妥当（S303 の深さ 64・名前 1024 は積を見ていない。64 段 × 1 KB の階層名を `SspComponent.name` と `names` に 2 つずつ持つので、Component 5000 個で RSS 650 MB という報告の再現と、コードの読みが合う） | 直した | `join` の結果が 4096 バイト（`MAX_PATH`）を超えたら誤りにし、System・Component・コネクタ・接続・System の束縛の総数（階層名を 1 つ抱える項目）に 10000 の上限（`MAX_ITEMS`）を付けた。接続の端点の名前（`join(path, 要素)`）も同じ上限で見る。Component だけでなくコネクタ・接続も数えるのは、項目ごとに階層名の複製を持つので、数えないと同じ積が残るため | `globe-mode-fmi` の `hierarchy_name_length_and_item_count_are_capped`（64 段 × 1 KB の最深部に Component は誤り、10001 個も誤り） | 入力に比例しない資源の上限（深さと長さを別々に絞るだけでは積が残る） |
| #110 分割配信の塊が壊れていると `ensure` が無限ループ | 妥当（直す前のコードで、塊 1 を `{}` にすると `check` が返らず、`<html>` だと 2 回目が固まるのを Node で再現。`fetchChunks` が読む前に `got` へ入れ、`names` のうち見出しのままのファイルを見ていなかった） | 直した | `fetchChunks` は、全部の塊を取って `JSON.parse` してから本文を入れ、索引が「その塊にある」と言うファイルが見出しのままなら誤りにして、その塊だけ `got` に入れない（次の呼び出しで取り直せる）。壊れた塊は「壊れている（URL）」の誤り。`ensure` の `for (;;)` にも、塊の数 + 1 回で誤りにする上限を付けた（進まない原因が他にあっても終わる） | `globe-mode-wasm/node/broken-chunks.mjs`（MSL 不要。塊が `{}`・`<html>` の各 2 回が固まらず誤りで返り、塊を直すと 3 回目で通る。固まるかは 5 秒の時間切れで落とす。`mise run wasm:node` に入れた） | 失敗しても終わる（終了条件のないループを書かない）／状態は成功してから進める |
| #117 パラメータの入力の途中で対象が変わる | 妥当（`apply` が呼ぶ時点の `this.target` を読み直す。偽の vscode での再現と、`globe/parameters` の応答待ちで差し替わる実際の経路が合う。重さは Nice: undo で戻せる） | 直した | `editParams` の最初に対象（`t`）と文書の版（`v`）を控え、`apply({method, args}, t, v)` に渡す。`apply` は控えた版から変わっていれば「文書が変わったので入れなかった」で戻る（S264 と同じ考え）。`edit`（ドラッグなど）は従来どおり呼ぶ時点の対象と版で、挙動は変わらない | `src/VSCode/globe-mode/test/panel-params-target.test.mjs`（`vscode` を偽物にして `Panel` を読む。応答待ちの間に `target` が B に変わっても A のクラスに書く、版が変わったら書かない。直す前は 2 本とも落ちる） | 対話の途中で文脈が変わりうるなら、開始時の文脈を使い続けるか、変わったら止める |
