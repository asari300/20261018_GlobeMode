## 1. 目的

S039 の持ち越し「Arrow での結果の受け渡し」（[roadmap.md](../../roadmap.md)）。Python パッケージ `globe_mode` の `Workspace.simulate` は時系列を CSV の文字列で返し、`table()` が polars で解析していた。wasm（S051）と Desktop（S076）はもう列で受け渡しているので、Python にも列の道を足す。

## 2. 決定と理由

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 受け渡しの形 | (c) 列ごとの `bytes`（f64 の little-endian）。Python 側で `memoryview(...).cast("d")` から `pl.Series` | 新しい依存が 0。(a) numpy は crate `numpy` と Python の numpy が要り、(b) Arrow IPC は `arrow` crate（依存が約 25 増える）と `pyarrow` が要る |
| API | `Workspace.simulate_columns(model, **settings)` が `simulate` と同じ dict に `columns`（名前 → `pl.Series`、`time` が先頭）を足し、`csv` は `None` | wasm の `simulate_columns` と同じ名前・同じ列の並び（`ColumnsLayout`） |
| `table()` | `columns` があればそれで表を作り、無ければ CSV を読む | CSV の道（`simulate`）は互換のため残す。`SimulationPlot`（S078）は `table()` 経由なのでどちらも受ける |
| Rust 側 | facade の `Workspace::simulate_with` の `run.trajectory` から py crate の中で列を作る（`no_csv = true`） | facade・protocol の型を変えない（別の WP が同時に変えている） |
| polars の作り方 | `memoryview` から `pl.Series` | 1 行で読める。`bin.reinterpret` で Array にしてから `reshape` すると 2〜5 倍速いが読みにくく、表を作る時間はもう 1 ms 未満なので採らなかった |

## 4. 再現手順

```bash
cd .git-worktree/s085-py-columns
uv sync --reinstall-package globe-mode   # wheel を作り直す
uv run pytest -q src/Python/tests        # test_columns.py: 列が CSV と完全に一致
```

10 万点 × 7 列（time と 6 状態の `Wide`、`Interval = 1e-5`、dopri45）で `simulate` + `table()` と `simulate_columns` + `table()` を 3 回ずつ比べた（手元の WSL）:

| 道 | 呼び出し | `table()` | 計 |
| --- | --- | --- | --- |
| CSV（`simulate`） | 311〜330 ms | 170〜175 ms | 485〜505 ms |
| 列（`simulate_columns`） | 78〜81 ms | 0.4〜0.7 ms | 79〜82 ms |

うち実行そのもの（`timings_ms.run`）は 44〜64 ms。CSV の道は CSV の文字列を作る・JSON に入れる・解析する分が約 420 ms 余る。

## 5. 次回

- big-endian の機械では `memoryview` の `"d"` が native-endian なので値が崩れる（コードに shortcut の注記）。対象の wheel（x86_64・aarch64）はどれも little-endian。
- Arrow IPC（ResultStore のファイル形式）は [roadmap.md](../../roadmap.md) の P3 の持ち越しのまま。
