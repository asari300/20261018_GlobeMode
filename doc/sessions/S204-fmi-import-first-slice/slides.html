FMI Import の最初の一切れ

FMU の共有ライブラリを自前の C ABI で読み込み、Co-Simulation を回して参照の CSV と全桁で一致した

Reference-FMUs 2.0・3.0 の 3 モデルが相対差 0。案 B（fmi crate）は入れられなかった
目的

このセッションでやること

  • ADR-0026 を Accepted にする。ユーザーの決定は「A、B 両方選択」
  • 案 A（自前の C ABI）で FMI 2.0・3.0 の Co-Simulation を 1 本通す
  • 案 B（crate fmi 0.8）を同じ trait の 2 つ目の実装として試す
  • CLI に globe fmu info と globe fmu run、Linux・Windows・macOS の手動 workflow
決定と理由

決めたこと

項目決定理由
A と BA を既定にして実装。B は同じ trait の実装として並べる設計。B は入れていない解釈は親のもの。B は zip 8.6.0 の脆弱性 4 件、FMI 3.0 の不具合
置き場新しい crate globe-mode-fmi-importExport と XML の利用者に libloading を背負わせない
信頼の境界展開だけ、読み込み、の 2 段。info は何も実行しない。run は 1 行警告FMU は任意のネイティブコード
展開zip slip・シンボリックリンク・2 GiB 超は失敗にする黙って飛ばさない

構成

案 B

fmi 0.8 を入れなかった理由

  • 推移的に zip 8.6.0 を引く。勧告が 4 件（RUSTSEC-2026-0367・0368・0369・0429）。FMU の展開にこの zip が使われる
  • Cargo.lock が 67 パッケージ増える。bzip2-1.0.6 が許可に無い。bindgen と libclang が要る
  • FMI 3.0 は Reference-FMUs で Instantiate が NULL（resourcePath の末尾に区切りが無い）
  • FMI 2.0 は動いた。参照の CSV と全桁で一致。戻す条件は ADR-0026 の (g)
