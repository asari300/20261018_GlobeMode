Android の APK を戻した

S308 で +9.1% 増えた APK を、塊を 1 本のパックにして +1.7% まで戻した

案 A（パック）と案 B（cap を上げる）を両方作って比べ、A を採った
目的

なぜ APK が増えたか

  • S308 で APK から MSL.json を外し、塊 838 本の分割配信にしたら arm64 で +1.24 MB
  • Tauri は asset を 1 つずつ brotli で圧縮して binary に埋める。16 KiB の塊は辞書を持ち越せない
  • 見積もり（brotli q9）: MSL.json 2.08 MB、塊 838 本 3.06 MB + 索引 0.19 MB。差 1.17 MB は実測の差 1.24 MB とほぼ合う
  • 残したいもの: 読み込み後の wasm の線形メモリ 62 → 14 MiB
決定と理由

2 つの案を両方作った

案中身
A（採用）Android の束だけ pack.bin に連結し、索引の pack.at に範囲。Worker は 1 回取って Blob.slice で塊を切り出す
B（外した）Android だけ塊の cap を 16 KiB → 256 KiB。塊は 461 本、先読みは 0

ユーザーの指示: 両方を実装して同じ表で比べ、優れた方を採る。採らなかった方は外す

選んだ理由

A が勝つ

  • APK: A は索引の約 0.2 MB だけが増える。B は cap を上げても塊が 446 本から減らず（ディレクトリごとに分ける）、0.5〜0.6 MB の損が残る
  • メモリ: A は読む塊が S308 と同じなので線形メモリも往復も同じ。B は先読みを効かせると取りすぎる（20 本で最大 341 MiB）
  • Blob: パックは Worker の JS ヒープに載せない（ArrayBuffer なら +15.2 MiB）
  • ブラウザ版は変えない（web.yml の束は c/*.json のまま）
次回

残したこと

  • 実機の WebView での Blob のメモリと速度（今回はエミュレータの smoke まで）
  • 索引（約 0.2 MB）を縮めれば APK がさらに戻る
  • ブラウザ版も 1 本にするかは、回線から塊だけ取れる利点とのトレード。今回は変えない
