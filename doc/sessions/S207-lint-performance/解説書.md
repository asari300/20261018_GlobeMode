## 1. 目的

S202 で NIF の `lint` を測ると、1 MB の本文で 2.2 秒、5.4 MB で 52 秒と、長さに対して急に遅くなった。`globe_mode_fmt::lint`（エディタの波線、`globe lint`、ウェブアプリ、Python・C・NIF が使う）と `format` で、2 乗になる原因を突き止めて直す。lint と format の結果は 1 文字も変えない。

## 2. 決定と理由

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 原因 | `lint` の中の 2 か所だけ。`format` は線形だった | 段ごとに測ると、字句解析・文の切り出し・配置・`format` は 5 MB で 0.1〜0.6 s。`lint` だけが 60〜90 s |
| 直し方 | 改行の位置の表を 1 度だけ作り二分探索で引く。長い行の位置は最初の行の表（`HashMap`）で引く | 最小の変更。結果の定義（先頭から数えた行・桁、最初に一致する行）をそのまま保つ |
| 歯止め | 本文を 2 倍にしたときの時間の比が 3 未満（3 回の最小値） | 絶対時間はランナーの揺れで落ちる。2 乗なら 4 になる。直す前のコードでは debug で 4.08 倍になって落ちる |

### 原因

[lint.rs](../../../src/Rust/mod/globe-mode-fmt/src/lint.rs) の 2 か所。

1. `line_col`（行・桁）が呼ばれるたびに `src[..start]` を先頭から数え直していた（`matches('\n').count()` と `rsplit`）。しかもクラス宣言ごとに、規則が止められていても、診断が無くても呼んでいた。クラスが n 個なら O(n × 本文の長さ)。`models`（診断 0 件）が 4.2 MB で 61 s かかったのはこのため。
2. `line-too-long` は、整形しても長い行ごとに、元の本文の全行を `position` で探していた。長い行が m 本なら O(m × 行数)。

### 直し方

1. 改行のバイト位置の表を 1 度だけ作る。`line_col` は `partition_point` で行を引き、その行の先頭から開始位置までの文字数が桁。
2. 元の本文の行（`trim` したもの）から最初の行番号への `HashMap` を 1 度だけ作る。

## 3. 計測

release、最小値（1 MB 以上は 1 回）。入力は使い捨てのプログラム（`~/.cache/globe-mode-s207/`）で作った。単位は秒。`models` は 1 つの package に model を n 個、`models-lint` は同じ形で名前が小文字・説明なしで診断が出るもの、`models-longcomment` は 80 桁を超えるコメントが各 model にあるもの、`equation` は 1 つの巨大な equation 節、`array` は 1 つの巨大な配列、`annotation` は annotation の多い宣言、`real` は MSL の `.mo` を連ねたもの。

## 4. 結果が変わらないこと

使い捨てのプログラムで、MSL 4.1.0 の全 `.mo`（2,556 本）と `src/Modelica`・`doc/research/upstream` の `.mo`（105 本）、合わせて 2,661 本を、直す前（main）と直した後で、次の 8 通りにかけ、結果のハッシュを比べた。

- `lint` と `format` の、行幅 80 と 30（行が長い診断が多く出る）、LF と CRLF（Windows の入力）の 2 × 2 × 2

不一致は 0 件（2,661 本 × 8 = 21,288 個のハッシュがすべて一致）。診断は（規則・行・桁・メッセージ）の並びと順、`format` は出力の文字列（失敗なら誤りの文言と位置）をハッシュした。

## 5. 歯止めの試験

`globe-mode-fmt/tests/format.rs` の `lint_time_grows_linearly`。n = 4000 と 8000 の model（名前が小文字、説明なし、長いコメント。診断は 3n 件）を lint し、時間の比（3 回の最小値）が 3 未満であることを確かめる。直した後は debug でも 1 s 以内に通る。直す前のコード（`git show HEAD:…/lint.rs`）に戻すと 4.08 倍で落ち、25 s かかる。
