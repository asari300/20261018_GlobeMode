エディタの補完を Rust につなぐ

S164 の穴 9。Svelte のエディタは予約語と本文の単語だけだった。ブラウザ（wasm）も Desktop（sidecar）も、Rust 側の候補が出る

Modelica.Blocks.Sources.Si と打つと Sine が出て、選ぶと入る
現状

何が困っていたか

  • LSP の補完（S053）は VS Code にだけつながっていた。UI は autocompletion({ override: [keywords, completeAnyWord] })
  • 型の位置で Modelica. と打っても、ライブラリのクラスは出ない
  • pin. の後ろは、同じファイルの Outline から探すだけ。extends した部品と、打ちかけで壊れた文書に弱い
決定と理由

決めたこと

項目決定理由
口Backend.completion(file, line, character)。wasm は completion、Desktop は rpc globe/completion。LSP の textDocument/completion と同じ計算S138 の定義ジャンプと同じ通し方。VS Code も広がった分がそのまま効く
引き方Resolver（定義ジャンプの解決）と LibraryTree をそのまま使う。新しい解析は入れない継承した部品も、import の別名も、定義ジャンプと同じ場所に行き着く
打ちかけ文書が壊れていたら、カーソルの行を空白にして読み直し、そのアウトラインで引くpin. を打った瞬間は必ず構文エラー。ここで引けないと使えない
CodeMirror予約語と本文の単語は即時。Rust の候補は非同期に足す。validFor と aborted で古い応答を捨てるRust が遅れても入力は止まらない
図

候補が出る位置

打っている所出る候補
語の頭（型の位置、式の中）予約語、そのクラスの部品（継承した分も）、文書のクラス、ライブラリの最上位
Modelica.Blocks. のようにクラスが先ライブラリの木の直下の子（種類と説明つき）。文書の入れ子のクラス、import の別名も
pin. のように部品が先その型の部品名（継承した分も）
文字列・コメントの中Rust 側は空

多くても 200 件。打ちかけの語に字が順に当たるものだけを返す

測定

応答時間（MSL 4.1.0 を読んだ状態）

1〜4 mswasm（Node）の応答。木の子・最上位・読み済みの型
約 0.3 sライブラリの型を初めて引くとき 1 回（ファイルの解析）
0.3 msDesktop（ネイティブ release）の 2 回目以降

wasm は呼び出しごとに作っていた「読んだライブラリのアウトライン」を持ち続けるようにした（毎回 260 ms だったのが 2 回目は 1 ms）。最初の 1 回の 0.3 s は 50 ms の目安を超える。持ち越し

結果

試験

  • Rust の単体 4 本: 型の位置でライブラリの子と絞り込み、継承した部品と壊れた文書、文字列・コメントの中は空、予約語と部品名
  • LSP の RPC 1 本: globe/completion と textDocument/completion が同じ候補
  • smoke.mjs（wasm:node）: MSL で Sources. の Sine、s. の y、文字列の中は空、応答時間
  • test_ui.py: MSL なしで部品 level（型 Real）と pin. の後ろの v・i。MSL ありで Sources.Si から Sine を選ぶと入る。GM-SMOKE の行は変えていない
次回

持ち越し

  • 最初の 1 回の 0.3 s（ライブラリのファイルの解析）を、読み込みの空き時間に先に回す
  • 本文の単語（completeAnyWord）と Rust の候補が同じ名前で 2 行出る
  • 同じファイルの型は、文書の別の行も壊れているときは引けない
  • 引数・シグネチャ・スニペット・修飾子名・import の自動挿入
