調査 1 · AdvancedSolenoid

AdvancedSolenoid は S6 の限界で、globe の誤りではない

何が起きているか

  • 電気側に接地の無い部品モデル。外に出したピン p・n は単体の検査では未接続で、flow が 0
  • 枝（抵抗・コイル・コンデンサ）8 本に対して節点 7 つ。枝 ≥ 節点 なので二部グラフには完全マッチングがある（S6 は 290 / 290 で通る）
  • しかし p と n のキルヒホッフの電流則は、各枝の電流の保存を通して数値的に従属。電位は差しか決まらない
  • omc は記号的な簡約（alias の除去）の後に 0.0 = 0.0 を見つけて「structurally singular」で止まる（-d=bltdump で確かめた）

構造の検査（二部グラフ）では捕まえられない数値的な特異。数値の検査（S10 のプリフライトで初期化のヤコビ行列の階数を見る）の候補にした。

図 · 初期化系の二部グラフ

t0 で成り立つ方程式をすべて集め、過剰と不足を別々に出す

不変量: 列 − 行 = 動的な状態 + 離散変数 + 初期化で決めるパラメータ − 与えた初期条件 = 要る数 − 与えた数。数だけの判定は差しか分からず、マッチングは過剰（extra）と不足（missing）を別々に出す（ADR-0011）。

決定と理由 · 組み方

初期化系の組み方（init_system.rs の match_init_system）

中身由来
列（未知数）未知数の族ごとに階数 0..=top（x、der(x)、…。代数 z も同じ）+ fixed = false で束縛の無いパラメータ + 束縛が推移的にそれを参照するパラメータ + 離散変数（d と pre(d) は 1 列）top は S7 の IndexReport::orders。添字は structure.rs と同じ鍵（unknowns_and_keys）で DaeStructure と揃える
行（方程式）(1) DAE の方程式 e と、それを 1..=d[e] 回微分したもの。(2) 初期方程式（der(x) は階数 1、x・pre(x) は階数 0）。(3) fixed = true の v = start。(4) パラメータの束縛 s.k = cd[e] は S7 の differentiations。(2)(4) はフロントエンドが InitStructure に新しく出した参照（位置ではなく構造なので without_ranges でも残る）
解き方最大マッチング（Hopcroft–Karp）と粗い DM 分解（S6 と同じ道具）。過剰な部分 = 対応の無い行から交互路で届く行と列（行が extra 本多い）。不足している部分 = 対応の無い列から届く列と行（列が missing 個多い）Pantelides（1988）の consistent initialization、Pryce の Σ 法と同じ考え方
組まないとき初期方程式を 1 つでも射影できない（has_incidence = false）、S7 が無いか打ち切り、長さが合わない → None。S8 は数と属性だけで判定（S007 と同じ結果）モデルを止めない。MSL の例題では 0 本

選ばなかった案: 初期方程式と fixed だけの小さなグラフ（インデックス 2 以上で拘束で決まる状態が見えず、Index.Pendulum に「2 個足りない」と誤る）。DaeStructure にパラメータの参照を足す（S6・S7 の入力を変えたくない。初期化で決めるパラメータがあるときだけ InitStructure 側で DAE をもう一度歩く）。Σ 法のオフセットから直接組む（S7 の結果で足りる。S007 の乱択テストで Σ 法と一致）。

決定と理由 · 診断

マッチングがあるときの S8 の診断（InitReport::diagnostics）

場合診断理由
extra > 0、過剰な部分に DAE の行が無く、離散変数も含まないGM-E8001（Error）。位置は最初の冗長の候補、補足に一覧初期条件どうしが同じ変数を決めている。確かに過剰
extra > 0、過剰な部分に DAE の行（拘束やその微分）がある、または離散変数を含むGM-W8004（Warning）。補足に冗長の候補と理由初期条件が拘束と同じ変数を決めている。整合する値なら冗長なだけ（omc も冗長な初期方程式を外して進む）。ADR-0009 の「Error は確かなときだけ」
missing > 0、不足 ≤ 不足している部分の fixed = false の離散変数の数柔らかい GM-W8001when の外で決まる離散変数には初期条件が要らない（MLS §8.6）が、その区別はまだ無い。ADR-0009 の約束のまま
missing > 0、それより多いGM-W8001（補足に未知数の一覧）+ 不足している部分の start の無い状態ごとに GM-W8002start 値を推定値として使う見込み。start も無ければ名指しする
両方両方を出す数だけの判定では片方しか出なかった（Init.RedundantAndMissing は数では 1 / 1 で合う）

マッチングが無いときは ADR-0009 の数と属性の判定のまま。is_balanced / extra() / missing() も、マッチングがあれば過剰と不足から、無ければ数から決める。

結果 · 最初のファネルで直したこと

InitSpringConstant の偽の「冗長 1・決まらない 61」

起きたこと

  • 1 回目のファネルで Mechanics.MultiBody.Examples.Elementary.InitSpringConstant に「冗長 1・決まらない 61」が出た。omc は過剰と言わない
  • 初期化で決めるパラメータ spring.c（fixed = false）は、部品の束縛 spring.spring.c = c を通してしか DAE に現れない
  • DAE の方程式は spring.spring.c を参照し、c は束縛にだけ現れる。だから c の列はどの行にも繋がらず、「決まらない」が 1 つ、対応する初期方程式が「冗長」として 1 つ、偽に出た

直し方（ADR-0011 の決定に足した）

  • 束縛が（推移的に）初期化の未知数を参照するパラメータも未知数（列）にする
  • その束縛 s.k = c を行にする（InitStructure::parameter_binding_refs）。束縛の式も初期方程式と同じ射影で参照を取れる
  • フロントエンドのテスト free_parameter_reached_through_a_binding_is_an_initialization_unknown

結果 · Rumoca の制約 (1)

inner の修正が outer に届かず、Fluid の初期方程式が消える

分かったこと（Rumoca v0.10.2、2026-10-19）

  • inner System system(energyDynamics = FixedInitial) を部品の outer System system から読むと、Rumoca は 型の既定（Free）で評価する
  • initial equation の if d == FixedInitial then p = ps_start; end if; が消える（initialization_owners() に無い）。型の既定を FixedInitial にすれば現れる
  • outer を使わない連鎖（parameter D b = a、部品のパラメータの修正、親のパラメータでの修正）は正しい。IfInit4 の 5 通りで切り分けた

記録

検証用のモデル Init.OuterModification（正しくは 2 / 2、Rumoca では 0 / 2 の GM-W8001）と db のテスト outer_modification_is_lost_by_the_compiler（Rumoca が直ったら落ちる）。上流への報告はユーザーが出す。

NonCircularPipes の食い違いはこれ

  • omc が冗長と言う mediums[1].p = 1e6 は、PartialDistributedVolume の if massDynamics == FixedInitial then mediums.p = ps_start。massDynamics は outer system から来る
  • globe の DAE ではこの初期方程式（2 本の配管で 8 本）が消えているので、S8 は「不足 4 / 40（冗長 0・決まらない 36）」。omc は「冗長 2」
  • マッチングの入力が欠けているのであって、マッチングの誤りではない
  • MSL の Fluid の例題 11 本が inner Modelica.Fluid.System system(energyDynamics = FixedInitial) の形

omc 側の補足

拘束の相手がコンパイル時に評価できないとき（boundary.p）、omc は「It was not possible to determine if the initialization problem is consistent」と「over specified」を出して、冗長な初期方程式を外して進む。

結果 · Rumoca の制約 (2)

外からの修正が、部品の中の同名の変数に漏れる

分かったこと（Rumoca v0.10.2、2026-10-19）

  • Part が Real theta1(fixed = true) と Joint joint(theta1(fixed = false)) を持ち、joint.theta1 = theta1 で結ぶ
  • Part part をそのまま使えば part.joint.theta1 は fixed = false（正しい）
  • 例題の形で Part part(theta1(fixed = true)) と修正すると、part.joint.theta1 と part.joint.der_theta1 も fixed = true になる（VariableView::fixed_scalar）
  • 別名の両方が fixed = true なので、マッチングは正しく冗長と言う。omc は別名を 1 つにまとめてから数えるので過剰と言わない

記録

  3. S9（代数ループ）・S10（プリフライト）。S10 に初期化のヤコビ行列の階数（UngroundedLoop・AdvancedSolenoid の数値的な特異）を入れる
  4. Checker のメモリの上限（P4 のプロセス構成が決まってから）
  5. Rumoca の制約の上流報告（ユーザーが出す。S004 の extends、GM-U、inner/outer、修正の漏れ の 3 項目に増えた）
  6. class_index の残り（for や if の中の connect、継承したクラスの入れ子）
  7. S8 の精密化の残り（射影に失敗したときの扱い、fixed = true の start が拘束と整合するかの数値の検査）

残したこと

  • AdvancedSolenoid の S8（冗長 1・決まらない 3）は omc が特異で止まるので照合できない
  • omc との S8 の照合で、別名の両方に fixed = true があるときの扱い。Rumoca の漏れが直れば RollingWheelSet* は消えるが、本当に両方に書いたモデルでは食い違いが残る
  • Rumoca が直ったら db のテスト 2 本が落ちるので、README と research/rumoca.md の記録を直す
  • スクラッチの小さなモデル（IfInit*、Alias*）はコミットしない。検証用のパッケージには代表の 2 本だけ入れた

omc は照合にだけ使い、globe check の判定には使わない（ライセンス、速さ、依存の方針は変えない）。
