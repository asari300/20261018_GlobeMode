### 2.1 #24: 範囲は annotation の中だけ

`annotation` は予約語なので、`annotation(` の `(` のグループの下を「annotation の中」と見ればよい。`Icon(graphics = {Line(…)})` のように、図形は必ず annotation の入れ子の下にある。外では `Rectangle`・`Line` などの名前が、継承の修飾・関数や record の呼び出し・短いクラス定義に現れるが、どれも並べ替えない。`Documentation(…)` の並べ替えと lint の `annotation-order` も同じ条件にそろえた。

### 2.2 #27: 一時ファイルと rename の細部

- **場所**: 同じフォルダに `<名前>.globe-tmp-<pid>`。拡張子が `.mo` でないので、走査（`collect_mo`）に拾われない。別のファイルシステムへの rename になることはない。
- **リンク**: `canonicalize` した先を書き換える。そうしないと rename が symlink そのものを通常のファイルに置き換えてしまう。
- **権限**: 元の `Permissions` を一時ファイルに写してから rename する（試験は Unix で 0o640 が保たれることを確かめる）。更新時刻は、書き換えたのだから新しくなる（`fs::write` と同じ）。
- **読み取り専用**: `fs::write` は読み取り専用のファイルに書けず誤りになる。rename だとディレクトリが書ければ黙って上書きできてしまうので、`readonly()` のファイルは先に `PermissionDenied` を返す（これまでと同じ終了コード 2）。
- **Windows**: `std::fs::rename` は `MoveFileExW` の `MOVEFILE_REPLACE_EXISTING` で既存のファイルを置き換える。ほかのプロセスが開いたままだと失敗するが、その場合も元のファイルは無傷で、一時ファイルは消す。`canonicalize` は `\\?\` 付きのパスを返すが、`rename`・`File::create` は受け付ける。全体検査の Windows のジョブで確かめた（作業記録に run）。
- **既知の限界**: ハードリンクと所有者は引き継がない（新しい inode になる）。`shortcut:` のコメントを main.rs に残した。
- **再現の手順**: `ulimit -f 1000`（512 バイト単位）で書き込みの上限を 512 KB にすると、上限を越えた書き込みで SIGXFSZ により終了コード 153 で落ちる。直す前は `big.mo`（6,377,780 バイト）が 512,000 バイトに切り詰められ、直した後は元のファイルが無傷（`cmp` で一致）で、一時ファイルだけが残る。一時ファイルは、落ちたときだけ残る（正常終了・誤りのときは消す）。

### 2.3 #28: 深さの上限 256

- **根拠**: 括弧の木を作る `layout::seq` は 1 段ごとに再帰し、木をたどる `flatten`・`render`（`flat`・`emit`・`expand`）・`annotation::apply`・`misordered` と、木の `Drop` も同じ深さだけ再帰する。入口の `seq` で深さを制限すれば、残りはすべて 256 段以下に収まる。1 か所の変更。
- **値**: 256。実際の `( [ {` の入れ子の最大は、MSL 4.1.0 の全 `.mo` で 22 段（`Media/Water/IF97_Utilities.mo`）、Buildings・AixLib を含めても 50 段（文字列とコメントを除いて数えた）。256 はその 5 倍で、人が書いたモデルが届かない。debug ビルドの 2 MB のテストスレッドでも 256 段の `format` が通る（試験は 256 段は通り、257 段は誤り）。
- **lint**: `lint` は `format` を呼び、失敗したら元の本文に戻る。100,000 段の入力で lint は診断を返して落ちない（試験が確かめる）。
- **誤りの位置**: 上限を越えた括弧の開きの位置。
- **Rumoca 側（持ち越し）**: Rumoca の構文解析は 100,000 段でも通る（`globe outline` が成功）が、検査（`globe check`）は 8 MB の main スレッドで 5,000 段まで通り 20,000 段で「stack overflow」になった。Rumoca は改変しない約束なので、ここでは直さない。直すなら入口（`GlobeDb::set_file` ではなく検査の入口）で入れ子の深さを数えて S0 の誤りにする。本文の上限が 1〜2 MB のウェブアプリは、Rumoca を呼ばず整形・lint だけなので、この件で落ちなくなった。

### 2.4 #32: BOM の扱い

| 面 | 扱い |
| --- | --- |
| `globe_mode_fmt::format` | 先頭の BOM を除いた本文を整形し、出力の先頭に BOM をそのまま付ける。`FormatError.offset` は BOM を含む位置（+3）。CLI の `fmt`（ファイル・標準入力）は `out == text` の比べも書き戻しも、この入口のおかげで BOM が残る。LSP の `globe/format` も同じ `format` を呼ぶので、全文の置き換えの編集は BOM を含む本文なら BOM を保つ（VS Code は BOM を本文に入れず、エンコーディングの設定で持つので、通常は BOM なしの本文が来る。VS Code の挙動は、拡張・LSP のコードを変えていないため【未確認】） |
| `globe_mode_fmt::lint` | BOM を除いた本文で読む。行・桁は BOM を除いて数える（エディタの見え方） |
| `GlobeDb::set_file` | 先頭の BOM を空白 3 個に置き換えて持つ。Rumoca に BOM は渡らず、バイト位置は渡した本文のまま（3 バイトの空白＝BOM の 3 バイト）。CLI や LSP が、渡した本文で診断の範囲を行・桁に直しても 3 バイトずれない。取り除く案は、呼び出し元が持つ BOM 付きの本文と位置がずれるので採らなかった |

BOM を `normalize.rs`（`source_shape`）で扱う案は、`outline` と `library_outlines` が正規化していない本文を Rumoca に渡すので、それだけでは直らない。そのため `set_file` に置いた。診断の桁は、BOM のある 1 行目に限り BOM の 1 文字ぶん右に出る（`globe outline bom.mo` の `model M (1:8)`）。
