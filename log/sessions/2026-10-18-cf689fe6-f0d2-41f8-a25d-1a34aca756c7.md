- **Zig:** the cbindgen tool is `MPL-2.0`. The generated header comes from your own code, and its `header=` setting lets you stamp your own license on it, which is how Apache OpenDAL does it. That the header isn't MPL-covered is the common reading **(unverified)**.

- **uniffi** is `MPL-2.0` and covers Kotlin, Swift and Python (Ruby too), with third-party wasm bindings. **wasm-bindgen** is `MIT OR Apache-2.0`. [uniffi](https://github.com/mozilla/uniffi-rs)

## 4. Licensing

- **Project license:** `MIT OR Apache-2.0`. It matches the Rust ecosystem, Apache adds a patent grant, and it's compatible with SUNDIALS (`BSD-3-Clause`), Monaco/CodeMirror (`MIT`), maxGraph and rumoca (`Apache-2.0`), and MPL-2.0 dependencies as long as those files stay MPL.

## 2. Lazy evaluation
We use salsa from Phase A.
- **Inputs:** `SourceFile{path,text}` (user files at `Durability::LOW`, MSL at `HIGH`), `LibraryRoot`, `Settings`.
- **Query chain:**
  1. `parse(file)`: Rumoca AST in an `Arc`, marked `no_eq`.
  2. `outline(file)`: neutral IR with `Eq`. This is the main **firewall**: whitespace or comment edits produce the same outline, so nothing downstream reruns.
  3. `class_index(root)`: built from `package.order`. MSL files are only parsed when a name lookup needs them.
  4. `class_interface(path)`: components after resolving `extends`, plus flow/stream/potential variables.
  5. From there, two independent queries:

  6. `flat(model)`: Rumoca resolve and flatten, run under `catch_unwind`.
  7. `dae_structure(model)`: neutral IR with `Eq`, a second firewall.
  8. `simulatability(model)`.
  9. `executable(model, backend)`: kept in an LRU cache.

- **S0 parse.**

- **S2 types:** type and dimension errors; unit mismatches are warnings.
- **S3 instantiate:** a `partial` top-level class, replaceables that were never redeclared.

## 4. FMI
**Import** (built on `fmi` 0.8 and `fmi-schema`):
- **ME:** `FmuMeSystem` implements `HybridSystem`, so it reuses the driver and every integrator.
- **CS:** `CoSimUnit{do_step, get/set, get/set_state, early_return}`.
- **SE (FMI 3):** `ScheduledUnit{activate_model_partition}` plus a priority-based clock scheduler.
- **Master algorithm:**
  - First: fixed-step Jacobi or Gauss–Seidel, with order taken from `ModelStructure` direct-feedthrough data; algebraic loops use fixed-point iteration.
  - Then: variable step with rollback when the FMU has `canGetAndSetFMUState`, FMI 3 event mode and early return, and SE.
  - The system topology comes from SSP or a `.gmsys` JSON file.
- **Platform limits:** native FMU binaries only load on desktop and Android. In the browser you can inspect `modelDescription.xml` and run FMUs that ship wasm binaries.

**Export:**
- **P5a (fast path):** Rumoca's `fmi2`/`fmi3` C templates produce source FMUs, and `cc` or `zig cc` builds the binaries for each target. We still need to check what license the generated template code carries.
- **P5b (own runtime):** `globe-mode-fmu-runtime`, built ahead of time per platform on the BSD-2 FMI headers, covering FMI 2 ME/CS and FMI 3 ME/CS/SE.
  - The model is either embedded as IR and interpreted, which needs no compiler and so also works from the browser and Android, or compiled through Rumoca's `rust-ode` template.
  - CS FMUs step with our own integrators.
  - `ModelStructure` comes from the BLT incidence.
  - `fmi-export` is only an option for FMI 3. FMI 2 export has no existing crate and must be written ourselves.

**Validation:**
- Reference-FMUs (BSD-2) for FMI 2 and 3 — BouncingBall, Dahlquist, VanDerPol, Stair, Feedthrough, Resource, Clocks — compared against their reference CSVs.
- Our exported FMUs must pass `fmpy.validate_fmu`, simulate in FMPy and in `fmusim`, and pass the FMU Compliance Checker (FMI 2 only).
- Round trip: export, re-import, then compare with a direct simulation using funnel tolerances.
- OMSimulator only as a subprocess.
