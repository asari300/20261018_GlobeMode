## 決めたこと

- **設計は (a) Rustler の NIF の crate `globe-mode-nif`**。(b) 「新しい crate を作らず `globe-mode-c` の `.so` を Elixir から呼ぶ」は、`:erlang` に dlopen が無いので C で NIF を書くことになり、結局 (a) より大きい（手書きの `enif_*` と resource の管理、`unsafe`）。Rustler なら resource・型の変換・dirty scheduler が属性 1 つで済む。
- Rustler の Hex パッケージ（`use Rustler`）は使わない。mix から cargo を呼ぶと mix の依存が増え、CI の道も変わる。`mise run elixir:test` が先に `cargo build --release -p globe-mode-nif` し、Elixir 側は `:erlang.load_nif` で `GLOBE_MODE_NIF` のパスを読むだけ。
- JSON のデコードは Elixir 1.18 の標準の `JSON`（`Jason` を足さない）。Elixir 側の Hex の依存は 0。
- `Workspace` は Send だが Sync でないので `ResourceArc<Ws(Mutex<Workspace>)>`。`check`・`graph`・`simulate` は DirtyCpu、`new`・`load_dir` は DirtyIo、`set_file`・`solvers` は普通の scheduler。
- `[lib] test = false`: cdylib の `enif_*` は BEAM が読み込むときに解決されるので、Rust の単体のテストの実行ファイルは作らない。試験は `mix test` 1 本。
- Erlang モジュール名は README の予定どおり `globe_mode_nif`（Gleam の `@external` から同じ名前で呼べる）。
- Gleam は持ち越し（Erlang の読み込み口と gleam test、CI の道がもう 1 本要る）。
- CI の BEAM は mise でなく `erlef/setup-beam` で入れる。mise の erlang 27.3.4.19 のビルドは glibc 2.43 を要り、ubuntu-24.04（glibc 2.39）では `beam.smp` が起動しない（run 41393072576 の `lang`）。手元（WSL）は mise のままで動く。
- RPi（ADR-0019）向けに、`elixir:test` は `MISE_DISABLE_TOOLS` に `elixir` があれば何もせず 0 で終わる。
