## 決めたこと

- **`route` を 1 つ作る**（`flatten.rs`）。`container`（最後の名前の定数・関数を宣言したクラス）と名前が通った package の列 `path` を末尾から合わせ、`Heir(h)`・`Static`・`Relative`・`Ambiguous` のどれかにする。S376 の `reaching`（関数だけ）と `via_class`（定数だけ、最後の名前の package だけ）はこれに置き換えた。1 つずつ道を足す案は、10 回目と同じ取りこぼしが出るので採らない。
- **`Static`（名前が宣言した側の外側を全部明示）は呼び出し元の package を持ち込まない**（#168）。issue は関数だけだが、定数の参照 `PP.n`（`P5.w = PP.n + 1` が 6 でなく 2）も同じ根なので同じ判定にした（omc で 2 を確かめた）。静的な呼び出し `Sub.f`・`P5.f` は、呼び出し元の差し替えの表・インスタンスの系統も持たない（`Target.stat`。#166）。外側が名前に出ない相対の名前（`Inner.f`・`f`）は今までどおり呼び出し元の package（`Relative`）。
- **宣言した側の束縛を、受け継いだ側を通して評価する**（#161）。`pkg_binding` は `heir` の系統（`chain`）に宣言したクラスが入れば `pkg_env`、入らず外側のクラスを受け継いでいれば、宣言した側の束縛の文脈の `heir` にそれを入れる（`with_heir`）。PKG の文脈の `heir` はこのとき初めて使う（`pkg_binding`・`call_target` は `ctx.heir.or(lineage.first())`）。
- **入れ子の package が内側の中にあれば 1 つの経路**（`Q.Inner` は `Q` の中。`r2.mo`）。内側を `heir` にして、定数は内側から外側へ `chain` をたどって引く。内側が外側の中にないとき（`A` の中の `Y` を `X extends A` を通して引く `X.Y.c`）は `Ambiguous` で断る。以前は最後の名前の package だけで決めて 7（omc と合う）だったが、`X.Z.c` が 2（6 のはず）だった。値にするには `heir` を経路にする必要があり、持ち越した。試験で断ることを固定した。
- **`dyn_const` を名前 3 つ以上に広げる**（#162）。`(…)` の修飾つきの差し替えを通る入れ子の定数は決めない（断る）。たどれない名前（`member_class` が `None`）・列挙の要素は今までどおり静的に引く（断ると `Medium.Choices.pT` のような形が通らなくなる）。
- **`alias_heir` は、型名の前半が宣言した側の外側のクラスの名前と食い違うときだけ引き直す**（#165）。issue の案は「`partial` の条件を外す」だけだが、毎回 `resolve` すると遅い（`alias_heir` のコメントに「毎回やると遅い」とある）ので、名前の比べ（`chain` の名前と型名の前半）を先にして、普通の `Modelica.Blocks.Interfaces.RealInput` は引き直さない。入れ子の型 `L.Sub.Y` は `class_res` の `owner` を `route` の `heir` にした（`h1.mo` の `w5.y`）。曖昧なら `ambiguous-package` で断る（`alias_heir` は `Res` を返す）。
- **`(…)` の修飾の鍵は、名前を含まない式は字面、含む式は場所**（#164）。場所だけだと、インスタンスごとに同じ `(c = 5)` を書いた 300 個が別の鍵になり、memo が効かない（最初の実装でこれに当たった）。名前を含む式は、同じ字面でも書いた場所の名前の解決が違いうるので場所で区別する。issue の最小案（インスタンスの `pfx` は一意なので `extra` を見ない）は、`for` の文脈と `cenv` の共有・同じ `pfx` の作り直しがあるので採らない。
- **文字列の表の上限は中身の総量**（#160。16 MiB。試験では 1 MiB に下げる。`MAX_ITERS` と同じ `cfg(test)` の流儀）。issue の「一時の `String` で比べる」案は `Val` が `Copy` なので採らない。
- **断ることが、MSL・公開ライブラリの平らにできた本数を減らさない**ことを、全体の検査と `libraries.yml` で確かめる（下）。最初の版で 6 本減った（`Medium.nX`・`Medium.nC` が「分からない」）。5 本は S377 の `reaches_mod`（`(…)` の修飾に届くかの判定）の粗さ、1 本は #163 の直しで外側の `(…)` が内側の `Medium` に届くようになったことが当たったので、判定を直した: 組み込み（`fill`・`zeros`・`String` など）は本体を読まない、`size(X, k)` は `X` の束縛が配列リテラル（内包なし）なら形だけを使う（`X` が修飾された名前なら見る）。`(…)` の修飾を当てて評価し直す案（S377 の持ち越し）は、関数の本体・入れ子の package・memo の鍵に `ovr` を通す必要があり、黙って違う値を出す道が増えるので採らない。
